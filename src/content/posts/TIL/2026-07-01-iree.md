# [TIL] 

This blog will cover primarily what IREE does in each pipeline stage and what the resulting IR looks like, using a small vector add program.

The central design is a separation between **host orchestration** and **device computation**. IREE lowers these at different rates. The GPU kernel can already be LLVM/NVVM IR while the surrounding program still uses Stream operations. Later, the kernel becomes an opaque payload while the host program becomes VM bytecode that calls the HAL runtime.

## The program and the evidence

Our input is a simple 4 elements vector add program:

```mlir
func.func @simple_mul(%arg0: tensor<4xf32>,
                      %arg1: tensor<4xf32>) -> tensor<4xf32> {
  %0 = "arith.mulf"(%arg0, %arg1)
      : (tensor<4xf32>, tensor<4xf32>) -> tensor<4xf32>
  return %0 : tensor<4xf32>
}
```

It computes `C[i] = A[i] * B[i]` for four elements. For inputs `[1, 2, 3, 4]` and `[10, 20, 30, 40]`, the expected result is `[10, 40, 90, 160]`.

## A map of the stages

To view the result of each pipeline stage, we can use `--compile-to` option. Many passes may run within a stage, and an artifact normally contains several dialects at once (progressive lowering).

| Boundary | Main responsibility | Representative operations or attributes |
|---|---|---|
| `input` | Normalize supported input into IREE’s common representation | `util.func`, tensor arithmetic |
| `abi` | Establish the application-facing calling convention | `hal.tensor.import`, `hal.tensor.export` |
| `preprocessing` | Apply requested preprocessing before global optimization | Tensor computation inside the ABI wrapper |
| `global-optimization` | Optimize and normalize structured tensor computation | `linalg.generic`, compute barriers |
| `dispatch-creation` | Form regions of work that can execute as dispatches | Dispatch regions and explicit computation boundaries |
| `flow` | Outline and organize executable computations | `flow.executable`, `flow.dispatch` |
| `stream` | Plan resource usage and execution dependencies | `stream.resource.alloca`, `stream.cmd.execute` |
| `executable-sources` | Materialize target variants and kernel interfaces | `hal.executable.variant`, binding layouts |
| `executable-configurations` | Select code generation strategy and parameters | `translation_info`, `lowering_config` |
| `executable-targets` | Lower kernels to target-oriented IR | `llvm.func`, `nvvm.read.ptx.sreg.tid.x` |
| `hal` | Lower orchestration and serialize device executables | HAL queues, fences, command buffers, executable binary |
| `vm` | Represent host control as VM instructions and imports | `vm.func`, `vm.call`, `vm.rodata` |
| Full output | Encode bytecode and package the runtime module | `.vmfb` |



## 1. Input, ABI, and preprocessing: make the program callable

### Input
It begins with `func.func` and tensor arithmetic. After public-function import, the function is represented using IREE’s utility dialect:

```mlir
util.func public @simple_mul(%arg0: tensor<4xf32>,
                            %arg1: tensor<4xf32>) -> tensor<4xf32> {
  %0 = arith.mulf %arg0, %arg1 : tensor<4xf32>
  util.return %0 : tensor<4xf32>
}
```

The responsibility of input conversion is to bring supported source representations into forms the rest of the compiler understands. A PyTorch-derived program would need a supported import/export path before reaching the same general pipeline. Our hand-written MLIR already has straightforward tensor arithmetic, so this part is trivial.


### ABI and Preprocessing
The next important transformation is the ABI boundary, which means separating external objects from internal ones, and define how the program interact with external environment. The public signature accepts and returns `!hal.buffer_view`:

```mlir
%a = hal.tensor.import %arg0 "input0"
    : !hal.buffer_view -> tensor<4xf32>
%b = hal.tensor.import %arg1 "input1"
    : !hal.buffer_view -> tensor<4xf32>
%c = arith.mulf %a, %b : tensor<4xf32>
%view = hal.tensor.export %c "output0"
    : tensor<4xf32> -> !hal.buffer_view
```

A buffer view is the runtime-facing object that describes a buffer together with tensor metadata. Inside the function, optimization still works on tensors. Reflection retains the original signature:

```text
sync func @simple_mul(%input0: tensor<4xf32>,
                     %input1: tensor<4xf32>) -> (%output0: tensor<4xf32>)
```

This separates the external object model from the internal mathematical representation. `import` and `export` mark that boundary; their presence alone does not imply a physical data copy.

Preprocessing is usually canonicalization. Since the program is small here there's really not much to canonicalize, so the result is the same as ABI pipeline stage output. Complete preprocessing & ABI results here:

```mlir
module {
  util.func public @simple_mul(%arg0: !hal.buffer_view, %arg1: !hal.buffer_view) -> !hal.buffer_view attributes {iree.abi.stub, iree.reflection = {iree.abi.declaration = "sync func @simple_mul(%input0: tensor<4xf32>, %input1: tensor<4xf32>) -> (%output0: tensor<4xf32>)"}} {
    %0 = hal.tensor.import %arg0 "input0" : !hal.buffer_view -> tensor<4xf32>
    %1 = hal.tensor.import %arg1 "input1" : !hal.buffer_view -> tensor<4xf32>
    %2 = arith.mulf %0, %1 : tensor<4xf32>
    %3 = hal.tensor.export %2 "output0" : tensor<4xf32> -> !hal.buffer_view
    util.return %3 : !hal.buffer_view
  }
}
```

## 2. Global optimization

Global optimization typically includes graph level rewrite, which means CSE, constant folding, etc. It is completely target agnostic.

In the example, the tensor-wide multiplication becomes a structured `linalg.generic`:

```mlir
indexing_maps = [
  affine_map<(d0) -> (d0)>,
  affine_map<(d0) -> (d0)>,
  affine_map<(d0) -> (d0)>
]
iterator_types = ["parallel"]
```

The three maps describe how the loop index addresses input A, input B, and output C. All use the same index. The body performs scalar multiplication and yields the result:

```mlir
^bb0(%a: f32, %b: f32, %out: f32):
  %product = arith.mulf %a, %b : f32
  linalg.yield %product : f32
```

Structured iteration makes the computation available to fusion, tiling, and distribution transformations. This artifact uses the first input tensor as the destination-style `outs` operand. Because the scalar body ignores `%out`, it does not depend on the old output contents. Tensor semantics at this stage do not establish an in-place update of the caller’s input buffer; later aliasing and bufferization decisions must preserve program semantics.

The surrounding `iree_tensor_ext.compute_barrier.start/end` operations constrain compiler transformations, such as reshape propagation across a boundary. They are only compiler level boundary, so not materialized and is possible to not materialize.

Global optimization works while the program still exposes tensor structure. For a larger model this is where transformations can operate across a broader computation graph, before dispatch boundaries limit which operations can be combined.

The result of global optimization:
```mlir
module {
  util.func public @simple_mul(%arg0: !hal.buffer_view, %arg1: !hal.buffer_view) -> !hal.buffer_view attributes {iree.abi.stub, iree.reflection = {iree.abi.declaration = "sync func @simple_mul(%input0: tensor<4xf32>, %input1: tensor<4xf32>) -> (%output0: tensor<4xf32>)"}} {
    %0 = hal.tensor.import %arg0 "input0" : !hal.buffer_view -> tensor<4xf32>
    %1 = iree_tensor_ext.compute_barrier.start %0 : tensor<4xf32> -> tensor<4xf32>
    %2 = hal.tensor.import %arg1 "input1" : !hal.buffer_view -> tensor<4xf32>
    %3 = iree_tensor_ext.compute_barrier.start %2 : tensor<4xf32> -> tensor<4xf32>
    %4 = linalg.generic {indexing_maps = [affine_map<(d0) -> (d0)>, affine_map<(d0) -> (d0)>, affine_map<(d0) -> (d0)>], iterator_types = ["parallel"]} ins(%1, %3 : tensor<4xf32>, tensor<4xf32>) outs(%1 : tensor<4xf32>) {
    ^bb0(%in: f32, %in_0: f32, %out: f32):
      %7 = arith.mulf %in, %in_0 : f32
      linalg.yield %7 : f32
    } -> tensor<4xf32>
    %5 = iree_tensor_ext.compute_barrier.end %4 : tensor<4xf32> -> tensor<4xf32>
    %6 = hal.tensor.export %5 "output0" : tensor<4xf32> -> !hal.buffer_view
    util.return %6 : !hal.buffer_view
  }
}
```

## 3. Flow

Flow is essentially doing "dispatch creation", which decides which operations belong in a unit of executable work. Before flow, all we have is a compute graph: it does not differentiate what computation needs to grouped to a single device for SPMD. A dispatch region, represented as a "flow.executable", is the atom for scheduling. For example, elementwise operations are natural for SPMD, so they will be submitted as a single dispatch. Reduction is not, since it changes the boundary (grid and block shapes will be changed).

After flow pipeline, the outer function now calls:

```mlir
%c = flow.dispatch
    @simple_mul_dispatch_0::@simple_mul_dispatch_0_elementwise_4_f32(%a, %b)
    : (tensor<4xf32>, tensor<4xf32>) -> tensor<4xf32>
```

The computation lives in a `flow.executable`, with an exported entry point and a nested function. That function receives two read-only dispatch tensors and one write-only output dispatch tensor. It loads the input slices, performs the Linalg computation, and stores the result.

This establishes a useful separation: the outer program says **which computation to invoke**, while the executable contains **how to compute its result**. A dispatch boundary is a scheduling and compilation boundary.

The export still contains:

```mlir
%x, %y, %z = iree_tensor_ext.dispatch.workgroup_count_from_slice()
```

This is a placeholder for workgroup-count calculation. A workgroup is a unit of distributed execution; on CUDA it corresponds to a thread block. The number of groups and the number of threads per group are different quantities, and neither follows directly from the four-element tensor shape at this point.

Full result after flow pipeline stage:


## 4. Stream

Stream pipeline makes resource sizes and scheduling visible. For example, when dispatching a workload, we need to answer the following question:
- Where is the input of the dispatch? Is it ready?
- Where can we execute this dispatch?
- When can host read back the result? 
To answer those questions, we need to track resource lifetime with allocation and dependencies.

The stream dialect rewrites the external resource access into `stream.tensor.import`, with explicity buffer size:
```mlir
%a = stream.tensor.import %arg0
    : !hal.buffer_view -> tensor<4xf32>
      in !stream.resource<external>{%c16}
```

The `external` resource category describes a lifetime that crosses program boundaries (for example, allocated on host and copied to device, or from another kernel).

The output is explicitly allocated:

```mlir
%result, %ready = stream.resource.alloca uninitialized
    : !stream.resource<external>{%c16} => !stream.timepoint
```

Allocation returns both a resource and a timepoint describing when it can be used. This `alloca` is a Stream resource operation, not a promise of CPU stack allocation.

Execution then waits for that resource and declares its accesses:

```mlir
stream.cmd.dispatch @simple_mul_dispatch_0::@... {
  ro %a[0 for 16] : ...,
  ro %b[0 for 16] : ...,
  wo %result[0 for 16] : ...
}
```

It annotates the input parameter with two 16-byte reads and one 16-byte write. The surrounding `stream.cmd.execute` returns a completion timepoint; `stream.timepoint.await` associates subsequent use of the result with completion of that execution.

Stream separates data dependencies from a particular queue or synchronization API. An earlier async-form Stream program may contain `stream.async.transfer` and `stream.async.dispatch`, with dependencies expressed through resource values. Scheduling and allocation lower that representation toward command regions and timepoints. `stream.async.transfer`, when present, represents a transition between resource states or affinities. It may require copying between memory spaces, but optimization can rewrite or remove transfers.

Inside the executable, `!stream.binding` parameters and `stream.binding.subspan` describe how to obtain tensor views from bound resources. The Linalg computation itself is still high level. IREE can reason about resource scheduling before committing to the final implementation of each kernel.

## 5. Executable sources

After this pipeline, the program has a default device affinity and a device declaration targeting CUDA. Operations such as allocation and execution are associated with that device.

The executable becomes:

```text
hal.executable @simple_mul_dispatch_0
  └─ hal.executable.variant @cuda_nvptx_fb
       ├─ hal.executable.export
       └─ builtin.module containing the kernel
```

A variant is an implementation for an executable target. The structure allows multiple implementations, even though this example has only one. The export establishes a pipeline layout with three storage-buffer bindings:

| Binding | Meaning | Access |
|---|---|---|
| 0 | A | Read-only |
| 1 | B | Read-only |
| 2 | C | Written by the kernel |

The kernel obtains data with `hal.interface.binding.subspan binding(0)`, and similarly for bindings 1 and 2. Device metadata records architectural capabilities: subgroup size choices, maximum block dimensions, and available workgroup memory. These are constraints for code generation.


It does not touch kernel internals.

## 6. Executable configurations: choose a lowering strategy

It adds the most compact explanation of the intended GPU mapping:

```mlir
translation_info = #iree_codegen.translation_info<
  pipeline = #iree_gpu.pipeline<TileAndFuse>
  workgroup_size = [32, 1, 1]
  subgroup_size = 32
>
```

The Linalg operation receives:

```mlir
lowering_config = #iree_gpu.lowering_config<{
  thread = [1], workgroup = [32]
}>
```

These attributes answer different questions:

- `workgroup_size` specifies a three-dimensional thread organization: 32 threads per block.
- `workgroup = [32]` tiles the one-dimensional iteration space into workgroup-sized chunks of 32 elements.
- `thread = [1]` gives a thread-level tile of one element.
- `subgroup_size = 32` selects a CUDA warp-sized subgroup.

The four-element problem therefore fits in one block, with only four threads needing to perform useful multiplication. At this boundary, that is the mapping implied by the configuration; the next artifact shows the generated control flow.

`TileAndFuse` selects a code generation pipeline. Its name does not imply that multiple operations were fused in this one-operation example. Keeping strategy selection separate from executing the transformations makes configurations inspectable and provides a place for user or tuning choices.

The buffer interface is also normalized. Binding subspans now produce `memref<4xf32, ...>` values, with `iree_codegen.load_from_buffer` and `store_to_buffer` bridging to the remaining tensor computation. Full bufferization has not happened merely because memrefs appear at the boundary.

## 7. Executable targets: make the GPU implementation concrete

In executable target pipeline, tensor operations, Linalg, and the configuration-only function body have been replaced by LLVM and NVVM operations. The entry now takes three `!llvm.ptr<1>` parameters. For this NVVM target, address space 1 is global memory. The export’s workgroup-count region returns `(1, 1, 1)`, and its workgroup size is `(32, 1, 1)`.

The kernel reads its thread ID:

```mlir
%tid = nvvm.read.ptx.sreg.tid.x range <i32, 0, 32> : i32
```

The resulting control flow is equivalent to:

```cpp
for (int i = threadIdx.x; i < 4; i += 32) {
  C[i] = A[i] * B[i];
}
```

Threads 0–3 each process one element. Threads 4–31 fail the initial bounds check and exit. No thread accesses an out-of-bounds element.

`llvm.getelementptr` computes element addresses; `llvm.load`, `llvm.fmul`, and `llvm.store` implement the arithmetic. The intermediate `vector<1xf32>` is a one-element vector representation, not a four-element vector operation per thread.

Pointer attributes such as `readonly`, `noalias`, and alignment information support subsequent optimization. There is no shared-memory cooperation or thread barrier because these multiplications are independent.

This boundary contains **target-oriented MLIR**, not PTX text yet. Meanwhile, the outer function still contains Stream operations. This is the clearest demonstration that kernel lowering and orchestration lowering proceed separately.

## 8. HAL: package the kernel and construct runtime execution

HAL completes the next major transition: the device implementation is serialized, and the surrounding schedule becomes explicit HAL operations.

### The kernel becomes executable data

The variant’s LLVM/NVVM module is replaced by:

```mlir
hal.executable.binary public @cuda_nvptx_fb attributes {
  data = dense<"0x..."> : vector<1484xi8>,
  format = "cuda-nvptx-fb",
  mime_type = "application/x-flatbuffers"
}
```

This 1,484-byte payload contains a CUDA executable FlatBuffer, including PTX and entry-point metadata. Decoding the artifact reveals:

```ptx
.version 7.6
.target sm_60
.address_size 64
```

Its core instructions read `%tid.x`, skip threads with IDs greater than 3, load A and B, execute `mul.rn.f32`, and store C. The earlier loop has simplified to one bounds check because a participating thread can execute at most one iteration.

The package contains PTX rather than final GPU machine instructions. The CUDA loading path and driver handle the subsequent device executable processing.

### Initialization creates reusable state

`util.initializer` code enumerates runtime devices, queries for CUDA and executable-format support, and creates a `!hal.executable`. Another initializer records and caches a command buffer through `@__simple_mul_memoize_apply`.

The recording uses binding slots 0, 1, and 2 and fixed workgroup counts `(1, 1, 1)`. It also records an execution barrier and finalizes the command buffer. This barrier orders command execution; it is not a barrier among CUDA threads.

Initialization prepares executable and command objects. It does not perform the model multiplication.

### Each invocation supplies resources and submits work

The public function checks the input views and underlying buffers, obtains a 16-byte output with `hal.device.queue.alloca`, and submits the cached command buffer through `hal.device.queue.execute.indirect`.

The indirect submission supplies the actual A, B, and C buffers for the recorded slots. This separates a stable command structure from per-invocation data. Therefore we can outline such dependency:

```text
Allocate C ──signal allocation fence──► Execute cached command buffer
                                               │
                                       signal completion fence
                                               │
                                      Await completion, return C
```

`hal.buffer_view.create` wraps the result with shape `[4]` and type `f32`. Returning that view does not itself copy the result to CPU memory. This function expects compatible input buffers; any upload performed by a calling tool is outside this function’s IR.

## 9. VM: encode orchestration as portable control code

Finally, the VM pipeline creates a `vm.module` with functions, imports, exports, globals, and read-only data.

HAL objects become VM references:

```text
!hal.buffer_view → !vm.ref<!hal.buffer_view>
!hal.device      → !vm.ref<!hal.device>
```

A HAL operation becomes a call to a runtime import:

```mlir
vm.import private @hal.buffer_view.buffer(
    %view: !vm.ref<!hal.buffer_view>) -> !vm.ref<!hal.buffer>

%buffer = vm.call @hal.buffer_view.buffer(%view)
    : (!vm.ref<!hal.buffer_view>) -> !vm.ref<!hal.buffer>
```

This is the runtime boundary: the VM executes control instructions and invokes the HAL module, whose implementation manages the device resources. Import `minimum_version` attributes constrain the HAL module interface version, not the LLVM revision. Strings and executable bytes become `vm.rodata`. The CUDA payload remains 1,484 bytes. `vm.const.ref.rodata` supplies references to it when initialization calls `@hal.executable.create`.


### Waiting can suspend VM execution

The fence wait becomes:

```mlir
vm.call.variadic.yieldable @hal.fence.await(...)
    -> ^resume(i32)
```

If the import completes immediately, control proceeds to the successor with its result. If it yields, execution resumes there after waiting. The successor checks the returned status, creates the output view on success, or executes `vm.fail` after cleanup on failure.

The synchronous public ABI requires completion before returning a result. Internally, the VM can support suspension and resumption; the HAL runtime may alternatively block a native thread in its synchronous mode. A synchronous application contract does not require every layer to implement waiting identically.
